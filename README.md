# Snowflake Cortex Cost Monitor

A Snowflake-native Streamlit application that helps DBA and platform teams monitor, attribute, investigate, and control the costs generated by Cortex Agents and Cortex Analyst.

## Quick Start

> **Current status:** The MVP runs locally in deterministic demo mode. Snowflake deployment files,
> SQL migrations, and validation scripts are implemented, but an account-specific deployment has
> not yet been performed.

### What You Need

| Purpose | Requirement | Notes |
| --- | --- | --- |
| Local demo | Python 3.11 | Python 3.11.16 is selected by `.tool-versions`. |
| Local demo | `venv` and `pip` | Included with Python; Conda is not required. |
| Snowflake deployment | Snowflake CLI | Used for connections, SQL execution, and Streamlit deployment. |
| Snowflake deployment | Snowflake account and role | Must be able to use the target warehouse, database, schema, and stage and create or update Streamlit objects. |
| Real cost data | Account Usage access | The application role needs access to the required Cortex Account Usage views. |

The locally verified versions are Python 3.11.16, Streamlit 1.50.0, and Snowflake CLI 3.14.0.

## Run Locally with Demo Data

Demo mode requires only Python. It does not require a Snowflake connection and never writes to
Snowflake.

### First-Time Setup

From the repository root:

```bash
python3 --version
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-dev.txt
```

The first command should report Python 3.11.16. On Windows, activate the environment with
`.venv\Scripts\activate`. No Conda installation is required.

This repository is configured for asdf through `.tool-versions`. If `python3` reports
`No version is set for command python3`, run:

```bash
asdf list python
asdf current python
```

If Python 3.11.16 is not listed as installed, install it once:

```bash
asdf install python 3.11.16
asdf reshim python
python3 --version
```

### Start the Demo

Keep the virtual environment active and run:

```bash
CORTEX_COST_DATA_MODE=demo python -m streamlit run streamlit_app.py
```

Open [http://localhost:8501](http://localhost:8501). Demo mode always displays a visible warning
and must not be used for financial reporting. Stop the server with `Ctrl+C`.

Do not add backslashes before underscores when entering the command in a shell.

### Start It Again Later

The dependencies only need to be installed once. For subsequent runs:

```bash
cd /Users/lh/ai/sf-ai-budget-monitor
source .venv/bin/activate
CORTEX_COST_DATA_MODE=demo python -m streamlit run streamlit_app.py
```

### Run Local Checks

```bash
python -m ruff format --check .
python -m ruff check .
python -m pytest
```

### Local Setup Troubleshooting

- **`No version is set for command python3`:** Confirm that `.tool-versions` exists in the
  repository and that asdf has Python 3.11.16 installed.
- **`.venv/bin/activate` does not exist:** The earlier `python3 -m venv .venv` command failed.
  Fix Python selection first, then create the virtual environment again.
- **`streamlit: command not found`:** Activate `.venv` and install `requirements-dev.txt`. Using
  `python -m streamlit` also guarantees that Streamlit comes from the active Python environment.
- **Port 8501 is already in use:** Stop the other Streamlit process or add
  `--server.port 8502` to the start command.

## Run Locally with Real Snowflake Data

Create `.streamlit/secrets.toml` for local development only:

```toml
[connections.snowflake]
account = "<organization-account>"
user = "<username>"
authenticator = "externalbrowser"
role = "<application-role>"
warehouse = "<reporting-warehouse>"
database = "<application-database>"
schema = "<application-schema>"
```

The file is excluded by `.gitignore` and must never be committed. Start in fail-fast Snowflake
mode so that a connection error cannot silently fall back to demo data:

```bash
CORTEX_COST_DATA_MODE=snowflake python -m streamlit run streamlit_app.py
```

## Deploy to Streamlit in Snowflake

The deployment uses Snowflake's warehouse runtime. Local dependencies come from
`requirements-dev.txt`; deployed dependencies come from `environment.yml`.

### 1. Verify Snowflake CLI

```bash
snow --version
snow connection list
```

Create a development connection if one does not already exist:

```bash
snow connection add
snow connection test --connection cortex-cost-dev
```

The connection should define the account, authentication method, deployment role, warehouse,
database, and schema. Prefer browser-based SSO, key-pair authentication, OAuth, or another
approved enterprise method. Do not place credentials in this repository.

### 2. Review the Target Objects

Before executing SQL, review these files and replace the default development identifiers if
necessary:

- `scripts/bootstrap_dev.sql`: warehouse, database, schema, and stage
- `sql/grants/001_application_grants.sql`: application role and object grants
- `snowflake.yml`: Streamlit identifier, stage, query warehouse, entrypoint, and artifacts

The development defaults are:

```text
Database:  CORTEX_COST_MONITOR_DEV
Schema:    CORTEX_COST_MONITOR
Warehouse: CORTEX_COST_MONITOR_WH
Stage:     CORTEX_COST_MONITOR_STAGE
Streamlit: CORTEX_COST_MONITOR
```

### 3. Bootstrap the Development Environment

Run the bootstrap with an approved administrative deployment role:

```bash
snow sql \
  --connection cortex-cost-dev \
  --filename scripts/bootstrap_dev.sql
```

After bootstrapping, ensure the `cortex-cost-dev` connection resolves to
`CORTEX_COST_MONITOR_DEV.CORTEX_COST_MONITOR`, then verify its context:

```bash
snow sql \
  --connection cortex-cost-dev \
  --query "SELECT CURRENT_ACCOUNT(), CURRENT_ROLE(), CURRENT_DATABASE(), CURRENT_SCHEMA(), CURRENT_WAREHOUSE()"
```

### 4. Apply SQL Migrations and Grants

With the local virtual environment active:

```bash
python scripts/apply_migrations.py --connection cortex-cost-dev
snow sql \
  --connection cortex-cost-dev \
  --filename sql/grants/001_application_grants.sql
```

The migrations create configuration tables, the curated `V_COST_EVENTS` contract, daily
aggregates, default budgets, and ownership mappings. Review grant SQL with the DBA team before
running it in a shared or production account.

### 5. Deploy the Development App

For the first deployment:

```bash
snow streamlit deploy cortex_cost_monitor \
  --connection cortex-cost-dev \
  --replace \
  --open
```

For later updates, add `--prune` only after confirming the local artifact list is complete:

```bash
snow streamlit deploy cortex_cost_monitor \
  --connection cortex-cost-dev \
  --replace \
  --prune \
  --open
```

`--prune` removes staged application files that no longer exist locally. It does not delete the
application's budget, mapping, or alert tables.

Retrieve and open the deployed URL later with:

```bash
snow streamlit get-url cortex_cost_monitor \
  --connection cortex-cost-dev \
  --open
```

### 6. Validate the Deployment

```bash
python scripts/validate_deployment.py --connection cortex-cost-dev
python scripts/reconcile_costs.py --connection cortex-cost-dev
```

Also verify manually that:

1. The Overview page opens with the intended role.
2. The displayed account, environment, currency, and refresh time are correct.
3. Summary totals reconcile with Audit Details.
4. Partial and unattributed costs are visible.
5. Unauthorized roles cannot access restricted data or Settings.
6. Existing budgets and ownership mappings remain unchanged after an application update.

### 7. Deploy to Production

Use a separate production connection and the same versioned migrations and source:

```bash
snow connection test --connection cortex-cost-prod
python scripts/apply_migrations.py --connection cortex-cost-prod
snow streamlit deploy cortex_cost_monitor \
  --connection cortex-cost-prod \
  --replace \
  --prune
```

Production migrations must be forward-only and idempotent. They must not reset budgets,
ownership mappings, alert history, or other business-owned configuration. Require deployment
approval and repeat smoke, reconciliation, and access-control checks after promotion.

### Snowflake Deployment Troubleshooting

- **The app cannot be found:** The CLI connection used for `get-url` must resolve to the same
  account, database, and schema used for deployment.
- **The app opens but cannot query data:** Check imported privileges on the `SNOWFLAKE` database,
  warehouse usage, schema usage, view grants, and row access policies.
- **A package cannot be installed:** Verify that its pinned version is supported by the selected
  Snowflake warehouse runtime and package channel.
- **Old application files remain:** Redeploy with `--prune` after reviewing the local artifact
  list in `snowflake.yml`.
- **Data appears stale:** Check Account Usage latency, task history, and the latest source event.
- **Agent compute credits are missing:** Agent SQL cost attribution can lag Agent usage by several
  hours and does not include Adaptive Warehouse queries.

## Product Overview

Cortex AI workloads can generate both direct AI service charges and indirect compute charges. A single Agent or Analyst request may invoke models, execute generated SQL, use a warehouse, or call other Snowflake services. These costs are difficult to understand when they are reviewed independently.

This application provides one operational view of Cortex expenditure. It enables the DBA team to answer four questions quickly:

1. How much are we spending?
2. Which Agent, Analyst workload, user, team, or warehouse is responsible?
3. Is the expenditure expected, anomalous, or approaching a budget limit?
4. Can an individual cost be traced back to its request and downstream queries?

## Goals

- Provide a unified view of Cortex Agent and Cortex Analyst expenditure.
- Separate direct AI charges from attributed downstream compute costs.
- Attribute costs to technical resources and business owners.
- Make unusual or high-cost activity easy to identify and investigate.
- Track actual expenditure against configurable budgets.
- Preserve request-level detail for audit and chargeback workflows.
- Run natively in Snowflake as a Streamlit application.

## Primary Users

### DBA and Platform Teams

- Monitor total Cortex expenditure and cost trends.
- Investigate cost anomalies and high-cost requests.
- Configure budgets and review threshold breaches.
- Validate cost attribution coverage and data quality.

### FinOps and Engineering Managers

- Review expenditure by team, project, environment, and cost center.
- Understand budget consumption and projected month-end expenditure.
- Support showback or chargeback reporting.

### Agent and Application Owners

- Review the cost and usage of the workloads they own.
- Identify inefficient, failed, or unexpectedly expensive requests.

## Cost Scope

The application divides expenditure into explicit cost categories so that costs remain understandable and are not double-counted.

### Direct AI Cost

Charges generated directly by Cortex AI services, including eligible Cortex Agent and Cortex Analyst activity.

### Attributed Compute Cost

Warehouse or serverless compute expenditure that can be linked to an Agent or Analyst request, including generated SQL executed as part of that request.

### Related Service Cost

Where reliable attribution is available, the model may be extended to include related services such as Cortex Search, embeddings, storage, or data transfer. These costs are outside the initial MVP unless explicitly approved.

### Cost Accounting Principles

- Store and display the original Snowflake credit amount.
- Display a monetary estimate using a configurable credit-to-currency rate.
- Keep direct and indirect costs separate in every detailed view.
- Present `Total Attributed Cost` only when its components are clearly identified.
- Prevent the same charge from being counted more than once.
- Display unattributed cost and attribution coverage explicitly.
- Retain the source identifiers needed to audit every calculated amount.

## Core Business Questions

The application must help users answer the following questions:

- What are today's, this week's, and this month's Cortex costs?
- How are costs divided between Agents, Analyst workloads, and downstream compute?
- Which Agents, semantic models, users, roles, teams, or warehouses are the largest cost contributors?
- Is cost growth caused by more requests or by a higher cost per request?
- Which requests, queries, or workloads are unusually expensive?
- How much expenditure was generated by failed or incomplete requests?
- Which budgets are approaching or exceeding their thresholds?
- How much cost cannot currently be attributed to an owner or workload?

1. Overview
2. Cortex Agents
3. Cortex Analyst
4. Cost Attribution
5. Budgets & Alerts

7. Settings

Global controls appear in the application header and apply consistently across pages:

Every page must show the data's last refresh time. Active filters must remain visible and must be preserved when users drill into another page.

## Page Requirements

### 1. Overview

#### Purpose

Give the DBA team an immediate understanding of current expenditure, budget status, major contributors, and items that require attention.

#### KPI Cards

- Total Attributed Cost
- Direct AI Cost
- Attributed Compute Cost
- Request Count
- Average Cost per Request
- Attribution Coverage
- Monthly Budget Utilization

#### Charts and Components

- **Daily Cost Trend:** Agent, Analyst, and attributed compute costs over time, with an optional budget reference line.
- **Cost Composition:** A donut chart showing the proportion of Agent, Analyst, and compute expenditure.
- **Budget Progress:** Actual month-to-date expenditure against the monthly budget.
- **Top Cost Contributors:** Ranked Agents, Analyst workloads, users, teams, or warehouses.
- **Attention Required:** Active budget breaches, detected anomalies, and unattributed costs.

#### Interactions

- Select a date to inspect that day's activity.
- Select a cost category to filter the page.
- Select a contributor to open its detailed Agent or Analyst view.
- Select an alert to open the relevant investigation context.

### 2. Cortex Agents

#### Purpose

Explain how individual Agents consume budget and identify the users, tools, models, and requests responsible for their costs.

#### KPI Cards

- Agent Cost
- Request Count
- Successful and Failed Requests
- Average Cost per Request
- Highest-Cost Request
- Period-over-Period Change

#### Charts and Components

- **Agent Cost Ranking:** Horizontal bar chart of total cost by Agent.
- **Cost and Request Trend:** Daily cost and request volume on aligned time axes.
- **Cost per Request Distribution:** Distribution of request costs, highlighting outliers.
- **Owner or Team Breakdown:** Cost grouped by assigned business owner.
- **Model and Tool Breakdown:** Direct cost split by model or tool when the source data supports it.
- **High-Cost Requests:** Detailed table of the most expensive requests.

#### Drill-Down Path

`Agent → User or Team → Request → Tool or Analyst Call → Query → Cost`

### 3. Cortex Analyst

#### Purpose

Monitor the cost of Cortex Analyst usage and connect semantic-model activity to generated SQL and downstream warehouse expenditure.

#### KPI Cards

- Analyst Cost
- Analyst Request Count
- Generated Query Count
- Attributed Warehouse Cost
- Average Cost per Request
- Failed Request Cost

#### Charts and Components

- **Semantic Model Cost Ranking:** Cost by semantic model or semantic view.
- **Analyst Cost Trend:** Direct Analyst cost and attributed compute cost over time.
- **Warehouse Cost Breakdown:** Compute cost grouped by warehouse.
- **Request Outcome Trend:** Successful, failed, and incomplete requests over time.
- **High-Cost Generated SQL:** Queries ranked by attributed compute cost.
- **User and Team Breakdown:** Analyst expenditure by consumer and owner.

#### Drill-Down Path

`Semantic Model → User or Team → Analyst Request → Generated SQL → Warehouse → Cost`

### 4. Cost Attribution

#### Purpose

Explain how direct AI activity leads to downstream compute expenditure and make gaps in attribution visible.

#### KPI Cards

- Total Attributed Cost
- Direct AI Cost
- Attributed Compute Cost
- Unattributed Cost
- Attribution Coverage
- Requests with Complete Lineage

#### Charts and Components

- **Cost Flow:** Flow from Agent or Analyst through tools and queries to the final cost category.
- **Direct vs. Indirect Cost:** Stacked comparison by workload, team, or date.
- **Attribution Coverage Trend:** Percentage of cost successfully attributed over time.
- **Unattributed Cost Breakdown:** Missing owner, request identifier, query identifier, or cost-center mapping.
- **Lineage Details:** Request-level table showing all linked identifiers and calculated amounts.

#### Attribution Quality

Every attributed record must include a confidence or quality status:

- Complete
- Partial
- Unattributed
- Excluded to prevent double-counting

### 5. Budgets & Alerts

#### Purpose

Allow DBA and platform teams to define cost limits and identify workloads that are likely to exceed them.

#### Budget Levels

- Account
- Environment
- Team or cost center
- Cortex service
- Individual Agent

#### Charts and Components

- **Budget Consumption:** Actual expenditure against the selected budget.
- **Budget Burn Trend:** Cumulative month-to-date expenditure with a budget reference line.
- **Month-End Forecast:** Projected expenditure compared with the configured limit.
- **Budget Status Table:** Current spend, remaining budget, utilization, and status.
- **Alert History:** Triggered threshold, timestamp, status, and resolution notes.

#### Alert Rules

- Support multiple thresholds, such as 70%, 90%, and 100%.
- Support absolute-cost and percentage-based thresholds.
- Avoid sending duplicate alerts for the same threshold and period.
- Keep an audit history of triggered and resolved alerts.
- Display alerts in the application for the MVP.

- Model and warehouse
- Request and session identifiers
- Query identifier
- Request outcome

- Attributed compute credits and cost

#### Interactions

- Filter and sort by any major dimension.
- Search by request, query, user, Agent, or semantic model identifier.
- Open the complete cost and lineage details for a selected row.

## Recommended Technology Stack

### Runtime and Language

- **Python 3.11** as the application language and runtime version.
- **Streamlit in Snowflake warehouse runtime** for the MVP.
- **Snowpark for Python** for Snowflake sessions, server-side transformations, and query execution.
- **SQL** for cost normalization, attribution, aggregation, security policies, and scheduled data preparation.

The warehouse runtime is recommended initially because the application is internal, Snowflake-native, and does not require arbitrary external packages. Snowflake provides Python, Streamlit, and Snowpark in the runtime. A container runtime can be evaluated later if the application needs a broader PyPI dependency set, persistent cross-session caching, or external services.

### User Interface and Visualization

- **Streamlit** for page composition, filters, session state, navigation, and interactive tables.
- **`st.navigation`** for explicit multipage routing and page access control.
- **Plotly** for interactive time-series, bar, stacked-bar, distribution, waterfall, and flow visualizations.
- **Native Streamlit charts and metrics** for simple KPI cards and lightweight charts.
- **Pandas** only at the presentation boundary after data has been filtered and aggregated in Snowflake.

The application should not load raw usage history into Pandas. Filtering, joining, aggregation, and cost calculations should run inside Snowflake, and only chart-ready result sets should be converted for rendering.

### Data and Persistence

- **Snowflake account and usage data** as the source for metering, request, and query activity.
- **Curated SQL views** to normalize source records and provide stable application contracts.
- **Scheduled tasks and aggregate tables** for expensive or frequently reused calculations when direct views do not meet the response-time target.
- **Configuration tables** for budgets, ownership mappings, currency conversion, and alert history.
- **Snowflake tags and role metadata** where available for team, environment, project, and cost-center attribution.

Application pages must query curated views or repositories rather than depend directly on raw system views. This isolates the UI from source-schema changes and keeps cost-accounting rules testable.

### Configuration and Deployment

- **`snowflake.yml`** as the Snowflake CLI project definition.
- **`environment.yml`** as the warehouse-runtime dependency definition, with critical runtime versions pinned.
- **`requirements-dev.txt`** for a standard Python virtual environment using `venv` and `pip`.
- **Snowflake CLI** for repeatable development and deployment with `snow streamlit deploy`.
- **Environment-specific Snowflake CLI connection profiles** for development, test, and production.
- **SQL migration scripts** for schemas, tables, views, tasks, grants, and seed configuration.

The main Streamlit entrypoint and `environment.yml` remain at the project root for warehouse-runtime compatibility. Deployment configuration must contain identifiers, not passwords or private keys.

### Testing and Code Quality

- **pytest** for unit and integration tests.
- **Ruff** for linting and code formatting.
- **Type hints** throughout domain, service, and repository interfaces.
- **Snowflake development schema** for integration tests against representative source data.
- **Fixture datasets** for deterministic testing of attribution, double-count prevention, budgets, and currency conversion.
- **CI pipeline** to run formatting checks, linting, unit tests, and SQL validation before deployment.

### Observability and Security

- **Python structured logging** for application events and failures.
- **Snowflake event tables and telemetry** where supported by the selected runtime.
- **Snowflake RBAC, row access policies, and secure views** for data-layer authorization.
- **Audit tables** for changes to budgets, mappings, conversion rates, and alert status.
- **No committed credentials or local secrets** in the application source tree.

## Application Architecture

The codebase follows a lightweight layered architecture:

```text
Streamlit pages and reusable UI components
                    │
                    ▼
        Application services and use cases
                    │
                    ▼
       Domain models and accounting rules
                    │
                    ▼
      Repository interfaces and Snowpark SQL
                    │
                    ▼
 Curated Snowflake views, tables, tasks, and policies
```

### Architectural Responsibilities

- **Presentation layer:** Displays data, collects filter input, and handles navigation. It must not contain cost-accounting SQL or business rules.
- **Application layer:** Coordinates use cases such as loading overview metrics, investigating a request, calculating budget status, and exporting audit data.
- **Domain layer:** Defines cost categories, attribution states, budget rules, currency conversion, and validation logic independently of Streamlit.
- **Data-access layer:** Encapsulates Snowpark sessions, parameterized queries, pagination, and result mapping.
- **Snowflake data layer:** Normalizes source data, calculates reusable attribution relationships, applies security policies, and prepares aggregates.

Dependencies point inward: pages may depend on services, services may depend on domain models and repository interfaces, and Snowflake repositories implement those interfaces. Domain logic must not import Streamlit.

### Structure Guidelines

- Keep `streamlit_app.py` small. It should configure the page, create navigation, and dispatch to page functions.
- Build pages from shared components instead of duplicating filters, KPI cards, or chart formatting.
- Keep SQL out of page modules. Pages call services, and services use repositories.
- Keep repository result sets aggregated and narrow enough for interactive rendering.
- Place reusable accounting rules in the domain layer and cover them with unit tests.
- Treat SQL views as versioned application interfaces and deploy them through ordered migrations.
- Make migration scripts idempotent where Snowflake object semantics allow it.
- Do not place credentials, production extracts, prompt content, or other sensitive data in the repository.

## Development and Deployment Workflow

1. Develop and test domain logic locally with fixture data.
2. Run unit tests and static checks before connecting to Snowflake.
3. Deploy SQL objects to an isolated development schema.
4. Run repository integration and reconciliation tests against that schema.
5. Run the Streamlit application locally or deploy it to the development account.
6. Deploy with Snowflake CLI using an environment-specific connection profile.
7. Run post-deployment smoke tests and verify the displayed refresh timestamp.
8. Promote the same versioned source and SQL migrations to test and production.

Use the full account bootstrap, migration, grant, deployment, and validation procedure in
**Deploy to Streamlit in Snowflake** above. After the first deployment, the standard update
command is:

```bash
snow streamlit deploy cortex_cost_monitor \
  --connection <connection-name> \
  --replace \
  --prune
```

The deployment process must not automatically modify production budgets, ownership mappings, or historical alert records.

## Data Dimensions

Where available, the cost model should preserve the following dimensions:

- Account
- Timestamp and reporting period
- Cortex service type
- Agent name
- Semantic model or semantic view
- User and role
- Warehouse
- Model
- Request identifier
- Session identifier
- Query identifier
- Request outcome
- Environment
- Team
- Project
- Cost center

Team, project, and cost-center ownership may require Snowflake tags or a maintained mapping table.

## Role-Based Access

- DBA and platform administrators can view all accounts and workloads in scope.
- FinOps users can view aggregated and detailed financial information.
- Workload owners can view only the Agents, Analyst workloads, teams, or cost centers they are authorized to access.
- Only authorized administrators can update budgets, mappings, and conversion rules.
- Access control must be enforced in the data layer, not only through hidden UI components.

## Non-Functional Requirements

### Performance

- Default to a 30-day reporting period.
- Target a page response time of three to five seconds for standard views.
- Pre-aggregate expensive reporting calculations where necessary.
- Paginate or progressively load large audit datasets.

### Data Freshness

- Display the last successful refresh time on every page.
- Display a warning when source data or calculated results are stale.
- Define the final refresh service-level objective after source-data latency is validated.

### Accuracy and Auditability

- Preserve Snowflake credits as the source financial unit.
- Make monetary conversion rules visible and configurable.
- Reconcile summary totals with request-level details.
- Identify missing data rather than silently estimating it.
- Retain a traceable relationship between source records and calculated costs.

### Usability

- Provide consistent filters, terminology, and cost categories across pages.
- Use clear chart labels and tooltips with both credits and monetary values.
- Make high-risk conditions visible without relying on color alone.
- Support common desktop resolutions used by DBA teams.

### Security

- Run within Snowflake's security boundary.
- Follow least-privilege access principles.
- Avoid exposing prompt content or query text to unauthorized roles.
- Record changes to administrative configuration.

## MVP Scope

The first release will focus on:

- One Snowflake account
- Cortex Agent and Cortex Analyst monitoring
- Direct AI cost reporting
- Attributed warehouse compute cost where reliable linkage is available
- Credit and monetary-value display
- Daily, weekly, and monthly trends
- Analysis by Agent, semantic model, user, role, team, and warehouse
- Request-level audit details
- Static budget configuration and in-application threshold alerts
- CSV export

## Future Scope

- Organization-wide, multi-account reporting
- Email and Slack notifications
- Automated anomaly detection
- Month-end cost forecasting
- Automated ownership and cost-center mapping
- Formal showback and chargeback reports
- Related Cortex Search, embedding, storage, and data-transfer costs

## MVP Acceptance Criteria

The MVP is complete when:

1. A DBA can view total Cortex cost for a selected reporting period.
2. Direct AI and attributed compute costs are shown separately.
3. Costs can be grouped by Agent, Analyst workload, user, role, team, and warehouse where source data is available.
4. A user can drill from a summary contributor to request and query details.
5. The application shows attribution coverage and unattributed cost.
6. A DBA can configure a budget and see when a threshold has been reached.
7. Summary totals reconcile with the detailed audit dataset.
8. Filtered audit data can be exported to CSV.
9. Role-based access prevents unauthorized users from viewing restricted cost details.
10. Every page displays the last data refresh time.
